Executive Summary
Ahsora Meds Academy should be built as a complete digital education and admissions platform rather than a simple brochure website. The public website must acquire and educate leads; the student portal must deliver courses, tests, mentorship and resources; the admissions layer must track university applications, documents, scholarships and visa stages; and the administration layer must allow staff to operate the business without requiring developer intervention for routine tasks.
The platform must have one central user identity, one source of truth for pricing and course data, one centralized backend, role-based permissions, audit logs, secure document storage, a reusable CMS, analytics and a scalable API layer.
Product Vision
The platform should make Ahsora Meds Academy feel like one unified system from the first website visit through course purchase, exam preparation, university selection, application management, visa processing and post-admission support.
Visitor -> Lead -> Counselling -> Student Account -> Course -> Tests/Mentorship -> University Shortlist -> Documents -> Application -> Scholarship -> Visa -> Admission -> Student Support
Core Business Objectives
Generate qualified leads from search, social media, direct traffic, referrals and paid campaigns. Convert leads into paid academic and consultancy services.
Deliver a professional student learning experience with courses, lectures, notes, tests, analytics and mentorship.
Manage admissions and consultancy operations in a structured CRM instead of spreadsheets and scattered chats.
Give students visibility into the status of documents, applications, scholarship and visa processes. Provide staff with role-specific dashboards and only the permissions they need.
Create a content engine that can rank for medical education, admission, scholarship and visa searches. Ensure that all critical information such as prices, dates, programme features and deadlines comes from centralized data and cannot silently conflict across pages.
Build for future expansion to additional exams, countries, universities, courses and services without redesigning the core architecture.

Recommended deployment model
Separate public frontend and authenticated application shell, but keep a unified brand and identity. Use a single backend/API layer as the system of record.
Use a relational database for transactional entities and relationships.
Use private object storage for student documents and media that should not be publicly accessible. Use CDN/image optimization for public media.
Use a queue/background job system for email, reminders, report generation, imports and other non-blocking tasks.
Use centralized logs, monitoring, error tracking and uptime monitoring.
Use separate development, staging and production environments with separate credentials and data boundaries.
Technology selection rule
The developer may choose the exact programming language/framework/database/cloud provider, but the choice must satisfy the requirements in this document. Lead Generation & CRM Requirements
Lead capture
All public enquiry forms must create a lead record rather than sending only an email.
Lead source must be recorded: organic, direct, referral, social, campaign, WhatsApp, phone, manual, etc.

Spam protection must exist without making the form unnecessarily difficult for genuine users. Each form submission must create an audit-safe event with timestamp and form origin.
Lead should optionally receive automatic confirmation email/WhatsApp/SMS depending on consent and provider availability.

Optional social login only if approved; it must not become the only access method. Email/phone verification.

For high-stakes information (visa rules, university requirements, legal/immigration guidance), the system must display source-backed information and human-review controls. AI output must not silently overwrite verified facts.

Final Instruction to the Development Team
Build Ahsora Meds Academy as a modular, API-driven, secure and maintainable platform. Do not implement the site as a collection of disconnected pages. The public website, student portal, testing system, admissions CRM, document workflow, scholarship and visa modules must share the same identity, core data model and business rules. Centralize data that must remain consistent (especially products, pricing, course access, deadlines and student records). Build for future expansion, but do not over-engineer features that have no current business value. Every sensitive operation must be authorization-checked on the server. Every important business state change must be auditable. Every routine content/product update that staff will need should be manageable from the admin portal without developer intervention.
This document is the functional baseline. The developer should produce a technical solution proposal mapped back to the requirements above, with any deviations clearly identified and approved before implementation.
